# 한걸음 디지털 V3 기술 아키텍처 설계

## 1. 설계 원칙

- `v2.0.0`의 기능, 라우트, Provider 공개 동작, SharedPreferences 키를 보존한다.
- 로그인과 네트워크가 없어도 기존 7개 연습을 모두 사용할 수 있어야 한다.
- V3 기능은 작은 어댑터와 저장소 경계 뒤에 추가한다.
- 실제 서비스, 실제 개인정보, 실제 결제와 연결하지 않는 연습 원칙을 유지한다.
- 서버는 필요한 문제가 확인된 뒤 도입하고, 단순한 미래 가능성 때문에 먼저 만들지 않는다.

## 2. 현재 V2 구조

### 2.1 실행 환경과 패키지

- Flutter 3.41.5 stable
- Dart 3.11.3
- Material 3
- 상태 관리: `provider 6.1.5+1`
- 라우팅: `go_router 16.2.4`
- 로컬 저장: `shared_preferences 2.5.3`
- 앱 아이콘·Splash 생성 도구는 개발 의존성으로만 사용

### 2.2 Provider

- 루트의 `LearningProgressProvider`가 포인트, 완료 횟수, 배지, 최근 기록, 접근성 설정, 보상 중복 방지 상태를 관리한다.
- `DailyMissionProvider`가 한국 날짜 기준 미션 선정, 완료, 추가 보상, 활성 미션을 관리한다.
- `PracticeProviderRegistry`가 7개 V2 콘텐츠의 장기 Provider 인스턴스를 보관한다.
- 각 콘텐츠 Provider는 임시 주문·선택·입력 상태만 관리하고 완료 시 기존 진행 Provider에 보상을 요청한다.
- 라우트에서는 기존 인스턴스를 `ChangeNotifierProvider.value`로 전달한다.

### 2.3 go_router

- `ShellRoute`가 홈, 연습하기, 미션, 내 정보 네 탭과 하단 내비게이션을 제공한다.
- 실제 연습 상세 라우트는 셸 밖에 있어 하단 탭과 겹치지 않는다.
- `PracticeLauncher`가 자유 연습 상태 초기화, 활성 미션 정리, 콘텐츠별 첫 라우트 이동을 맡는다.
- 모드 선택과 미션 진입은 기존 콘텐츠 ID와 라우트 이름을 유지한다.

### 2.4 SharedPreferences

저장 범위는 다음과 같다.

- 포인트
- 콘텐츠·모드별 완료 횟수
- 첫 완료 배지
- 최근 연습 기록
- 완료 세션 보상 토큰과 중복 지급 방지 값
- 한국 날짜 기반 오늘의 미션 날짜, 선택 ID, 완료 ID, 보상 ID, 이전 조합, 선정 빈도, 활성 ID
- 글자 크기, 화면 대비
- 온보딩 완료 상태

V3는 이 키의 이름이나 의미를 바꾸지 않는다. 전체 키 목록과 마이그레이션 규칙은 `V3_데이터_마이그레이션.md`에 둔다.

### 2.5 개인정보·권한·네트워크

- 릴리스 AndroidManifest에는 실제 연락처, 사진, 카메라, 위치, 생체, 금융 권한이 없다.
- 디버그·프로필의 인터넷 권한은 Flutter 개발 도구용이며 앱 기능의 네트워크 연결을 뜻하지 않는다.
- Firebase, 로그인, 분석 SDK, 광고 SDK, 결제 SDK가 없다.
- 사진, 연락처, 주민등록번호, 카드번호, 계좌번호, PIN, 지문은 실제로 읽거나 저장하지 않는다.

### 2.6 테스트와 문서

- 33개 테스트 파일과 183개 테스트가 V2 기준선이다.
- Provider 단위 테스트, 저장 복원·중복 보상 테스트, 라우팅·위젯·320dp 반응형 테스트가 있다.
- `docs/`에는 각 V2 콘텐츠, 미션, 디자인 시스템, 진입 구조, 접근성 점검 문서가 있다.

## 3. 아키텍처 대안 비교

| 항목 | 로컬 중심 | Firebase 중심 | 자체 서버 |
|---|---|---|---|
| Flutter 연결 | 현재 구조를 그대로 감쌀 수 있음 | 공식·검증된 SDK가 많음 | REST/API 클라이언트 직접 설계 |
| 초기 난이도 | 낮음 | 중간 | 높음 |
| 월 운영비 | 거의 없음 | 무상 구간 후 종량제 | 서버·DB·백업·모니터링 지속 |
| 개인정보 | 기기 밖 전송 최소 | 클라우드 처리와 규칙 설정 필요 | 모든 처리 책임을 직접 부담 |
| 오프라인 | 매우 강함 | 캐시 가능하나 충돌 설계 필요 | 별도 로컬 큐 필요 |
| 확장성 | 단일 기기에 적합 | 빠른 초기 확장 | 설계에 따라 가장 유연 |
| 장애 대응 | 앱 내부 복구 | 서비스 상태·보안 규칙 대응 | 24시간 운영 책임 |
| 백업 | 앱 삭제 시 소실 | 관리형 백업·내보내기 설계 | 직접 백업·복구 훈련 |
| 1인 개발 | 가장 적합 | 계정·원격 공지 단계에 적합 | 운영 역량이 확보된 뒤 적합 |

Firebase를 쓸 경우 Authentication, Firestore, Cloud Functions, FCM, Crashlytics가 후보지만 필요한 제품만 선택해야 한다. 무상 구간도 제품별 제한이 있으며 Blaze는 종량제이므로 [Firebase 가격](https://firebase.google.com/pricing)을 확인하고 예산 알림을 설정한다.

자체 서버안은 FastAPI, PostgreSQL, OAuth/JWT, 관리자 웹, 배포·백업·모니터링으로 구성할 수 있다. 데이터 모델과 운영 통제는 가장 좋지만 V3 기본 범위에는 과도하다.

## 4. 권장 아키텍처: 로컬 우선, 교체 가능한 경계

```text
UI / Pages
  -> Feature Providers
    -> Domain Services
      -> Repository Interfaces
        -> V2 SharedPreferences adapters (V3 기본)
        -> Remote adapters (향후 선택)
```

V2 Provider를 한 번에 재작성하지 않는다. 새 기능부터 인터페이스 뒤에 구현하고, 기존 진행 데이터는 `LearningProgressProvider`를 감싼 어댑터로 읽는다.

### 4.1 권장 모듈

```text
lib/
  core/
    storage/
      schema_version.dart
      migration_runner.dart
    audio/
      audio_guide_service.dart
    notices/
      notice_repository.dart
    entitlement/
      entitlement_repository.dart
  features/
    help/
    subscription_info/
    sms_practice/
    self_checkout/
```

실제 경로는 구현 시 기존 폴더 관례에 맞추되 다음 책임은 분리한다.

- `LocalProgressRepository`: 기존 Provider와 Preferences를 대신하지 않고 안전하게 감싼다.
- `AudioGuideService`: TTS 호출, 중지, 속도, 접근성 중복 방지.
- `NoticeRepository`: 번들 공지·FAQ와 향후 원격 읽기 구현의 공통 계약.
- `InquiryService`: 이메일 연결과 향후 서버 문의를 분리.
- `EntitlementRepository`: 무료·구독 권한을 조회하는 계약. V3 1차 구현은 기존 무료 권한만 반환.
- `ContentCatalog`: V2와 신규 연습의 제목, 아이콘, 모드, 무료 여부를 한곳에서 제공.
- `AuthRepository`, `SyncRepository`, `BillingRepository`: V4 검토 전에는 인터페이스도 과도하게 상세화하지 않는다.

## 5. 음성 안내 설계

### 5.1 동작

- 각 화면은 전체 위젯 트리가 아니라 검토된 핵심 문장만 음성 서비스에 전달한다.
- 사용자 동작으로 `다시 듣기`를 실행한다.
- 자동 읽기는 기본 끔이며 화면 전환마다 이전 발화를 중지한다.
- 속도는 느리게/보통 두 단계부터 시작한다.
- 음량은 별도 개인정보나 설정을 저장하지 않고 Android 미디어 음량을 따른다.

### 5.2 접근성

- TalkBack 활성 여부를 확인할 수 있으면 자동 읽기를 억제한다.
- 확인이 어렵다면 자동 읽기 설정 시 중복 재생 가능성을 알리고 기본값을 끈다.
- 음성 버튼에는 읽을 대상과 재생 상태를 Semantics로 제공한다.
- TTS 실패나 엔진 부재가 연습 진행을 막지 않는다.

### 5.3 구현 후보

`flutter_tts` 같은 검증된 패키지 또는 작은 플랫폼 채널을 비교한다. 패키지를 추가하기 전에 Android 지원 범위, 유지보수 상태, 앱 크기, 개인정보 처리 내용을 검토한다. 기본 구현은 기기 내 TTS를 우선하며 클라우드 음성 API를 사용하지 않는다.

## 6. 공지·FAQ·문의 설계

### V3 1차

- `assets/content/notices.json`, `faq.json` 같은 번들 데이터
- 앱 버전에 포함되어 완전 오프라인에서 동작
- 문의는 사용자가 누른 경우에만 이메일 앱을 열고 본문을 직접 확인하게 함
- 앱 버전만 선택적으로 첨부하고 기기 ID나 기록은 첨부하지 않음

### 원격 확장

- 공지 변경 빈도가 실제로 높을 때 HTTPS 읽기 전용 엔드포인트 도입
- 마지막 정상 응답 캐시와 번들 기본값 유지
- 관리자 인증, 게시 예약, 감사 로그는 운영 도구와 함께 설계
- 원격 장애가 연습 기능에 영향을 주지 않음

## 7. 구독 아키텍처 초안

### 7.1 권한 모델

```text
Entitlement
- freeV2Content
- premiumNewContent
- extendedVoice
- extraMissions
- detailedReport
```

기존 7개 콘텐츠는 항상 `freeV2Content`로 접근 가능해야 한다. 네트워크 오류나 결제 상태 확인 실패 때 기존 무료 기능을 잠그지 않는다.

### 7.2 상태 모델 후보

- `free`
- `trial` (도입 여부 미정)
- `active`
- `gracePeriod`
- `onHold`
- `expired`
- `unavailable`

V3 설계 화면은 이 가짜 상태로만 테스트하며 실제 구매 토큰이나 결제 SDK를 추가하지 않는다.

### 7.3 Play와 스텝페이

- Play 배포 Android 앱 안에서 판매하는 디지털 구독은 [Google Play Billing](https://developer.android.com/google/play/billing)을 기본안으로 검토한다.
- 구매 검증, 승인, 갱신·유예·보류 처리는 보안 백엔드를 권장한다. [Billing 백엔드 문서](https://developer.android.com/google/play/billing/backend)를 구현 시점에 따른다.
- 한국의 대체 결제는 등록, 사용자 선택 UI, 전용 API, 거래 보고 같은 요건을 충족해야 한다. 외부 링크를 임의로 제공하지 않는다.
- 스텝페이는 웹 판매와 운영 관리, API·웹훅 후보로 평가하되 Play 앱 내 흐름은 최신 정책 검토 뒤 확정한다.
- 가격, 자동 갱신, 청구 주기, 체험 종료와 해지는 [구독 정책](https://support.google.com/googleplay/android-developer/answer/9900533?hl=ko)에 맞게 구매 전에 명확히 고지한다.

## 8. 계정과 동기화의 향후 경계

계정이 필요해지면 게스트 데이터를 먼저 보존한 뒤 명시적 `기기 기록 연결` 절차를 제공한다. 자동으로 서버 계정에 덮어쓰지 않는다.

- 인증 토큰은 SharedPreferences가 아니라 Android Keystore 기반 보안 저장소에 둔다.
- 서버 API는 사용자 ID가 아닌 인증 주체와 권한을 기준으로 데이터에 접근한다.
- 업로드 이벤트에는 고유 ID와 스키마 버전을 붙여 재시도를 멱등 처리한다.
- 로그아웃 시 서버 기록은 유지하되 기기 사본 유지/삭제를 사용자가 선택한다.
- 탈퇴 시 서버 삭제 대기 기간, 즉시 접근 차단, 기기 데이터 선택 삭제를 분리한다.

## 9. 개인정보와 보안

| 구분 | 예시 | 저장 위치 | 원칙 |
|---|---|---|---|
| 필수 로컬 | 포인트, 완료 횟수, 배지, 설정 | 기기 | 기존 키 유지, 기록 초기화 제공 |
| 선택 로컬 | TTS 사용·속도, 읽은 공지 | 기기 | 기능별 끄기·삭제 가능 |
| 향후 서버 최소 정보 | 계정 식별자, 동기화 이벤트 | 서버 | 계정 기능 동의 후에만 |
| 문의 선택 정보 | 이메일, 문의 내용, 앱 버전 | 메일/서버 | 자동 첨부 최소화, 보유 기간 고지 |
| 수집 금지 | 주민번호, 카드·계좌, PIN, 생년월일, 지문, 실제 사진·연락처 | 어디에도 저장 안 함 | 가상 데이터만 사용 |

- 전송이 생기면 TLS를 사용하고 서버 저장 데이터는 관리형 암호화를 적용한다.
- 토큰과 비밀은 로그에 남기지 않고 식별자는 마스킹한다.
- 오류 보고에 화면 입력값과 연습 선택 상세를 기본 포함하지 않는다.
- 계정 기능에는 탈퇴, 데이터 삭제, 필요한 경우 내보내기 절차를 함께 제공한다.
- 보유 기간은 목적별로 짧게 정하고 만료 삭제를 자동화한다.

## 10. 장애와 오프라인 원칙

- 네트워크가 없어도 V2와 로컬 신규 콘텐츠는 실행 가능해야 한다.
- 공지 서버, 문의, 구독 상태 확인 실패는 해당 보조 기능에만 영향을 준다.
- 마지막 확인된 구독 상태를 짧게 캐시하더라도 기존 무료 기능은 항상 연다.
- 마이그레이션, 동기화, 결제 검증 실패를 사용자 포인트 초기화로 해결하지 않는다.
- 원격 어댑터에는 타임아웃, 제한된 재시도, 취소, 명확한 오프라인 상태를 둔다.

## 11. 아키텍처 결정

V3 1차는 로컬 중심을 채택한다. Firebase나 자체 서버는 연결하지 않고 저장소·음성·공지·권한 경계만 만든다. 원격 공지의 운영 필요, 계정 복원 수요, 구독 모델의 사용자 검증 결과가 모이면 Firebase와 자체 서버를 다시 비교하는 ADR을 작성한다. 이 순서가 V2 데이터 안정성, 1인 개발의 운영 가능성, 개인정보 최소화를 가장 잘 만족한다.

## 12. 연습 포인트 혜택 아키텍처

포인트 혜택은 기존 `LearningProgressProvider.totalPoints`를 읽되 기존 포인트 키나 지급 메서드를 소유하지 않는다.

자유 연습 0점, 따라 해보기 10점, 혼자 해보기 20점과 오늘의 미션 추가 10점 정책을 그대로 사용한다. 구독 상태는 점수 계산과 분리하고, 접근성·힌트·안전 기능은 누적 포인트 보상으로 잠그지 않는다.

```text
기존 완료 보상 성공
  -> RewardEvaluator.evaluate(previousPoints, currentPoints)
    -> RewardCatalog
    -> RewardStateRepository
      -> SharedPreferences (작은 ID·선택 상태)
  -> RewardCelebrationCoordinator
```

- `RewardCatalog`: 변경되지 않는 ID, 종류, 점수 기준, 슬롯, 접근성 이름
- `RewardEvaluator`: 기준 통과와 소급 지급 계산, 같은 ID의 멱등성 보장
- `RewardStateRepository`: 획득 ID·시각, 현재 선택, 안내 완료 상태 저장
- `RewardCelebrationCoordinator`: 여러 보상을 한 묶음으로 한 번만 표시
- `CharacterDecoration`: 기존 `CustomPainter`의 머리·얼굴·목·옆면 레이어
- `HomeThemeSelection`: 배경 장식만 변경하며 대비·접근성 토큰을 우선

보상 기능이 실패하거나 비활성화되어도 기존 포인트 지급과 완료 처리는 성공해야 한다. 총점을 복구 가능한 진실 공급원으로 두어 다음 실행에서 누락된 해제를 다시 계산한다. 수십 개의 보상은 SharedPreferences로 충분하지만 포인트 거래 원장, 원격 동기화, 수천 개 이벤트 또는 트랜잭션이 필요해지면 Drift/SQLite를 검토한다.

상세 모델과 화면·테스트 규칙은 [V3 포인트 혜택 설계](V3_포인트_혜택_설계.md)를 따른다.

초기 기준은 100, 300, 500, 800, 1,200, 1,600, 2,000, 3,000, 5,000점이다. 1,600점과 3,000점처럼 한 기준에서 둘 이상의 보상을 해제해도 각 보상은 서로 다른 안정적인 카탈로그 ID를 갖는다. 기준이나 표시 이름을 바꿔도 ID를 재사용하거나 이미 획득한 보상을 회수하지 않는다.
