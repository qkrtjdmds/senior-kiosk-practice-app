# V3 포인트 데이터 모델 구현

## 1. 구현 범위

이번 단계는 누적 연습 포인트 보상의 데이터 계약만 구현한다.

- 타입 안전한 보상 종류
- 불변 보상 정의와 사용자 상태
- 안정 ID 12개의 정적 카탈로그
- SharedPreferences 저장소와 중단 복구
- 연습 기록 초기화 연동
- 손상·미래 데이터의 비파괴 처리

기존 사용자 소급 지급, 포인트 완료 흐름의 자동 해제, 홈·내 정보·보상 화면, 캐릭터 장식, 홈 테마, 축하 화면은 포함하지 않는다. 앱 시작 흐름도 저장소를 호출하지 않으므로 보상 키를 자동 생성하지 않는다.

## 2. 코드 구조

| 파일 | 책임 |
|---|---|
| `lib/features/rewards/reward_models.dart` | `RewardType`, `RewardDefinition`, `RewardState` |
| `lib/features/rewards/reward_catalog.dart` | 정적 카탈로그, 검증·정렬·조회 |
| `lib/features/rewards/reward_repository.dart` | SharedPreferences 저장·복원·선택·초기화 |
| `lib/core/data_migration/preference_keys.dart` | `V3RewardKeys` 중앙 키 목록 |
| `lib/features/learning/learning_progress_provider.dart` | 기록 초기화 시 기존 보상 키 제거 |

UI Provider는 추가하지 않았다. 아직 화면이 없고 자동 해제를 금지하는 단계에서 Provider를 앱 루트에 만들면 불필요한 앱 시작 읽기와 rebuild가 생길 수 있기 때문이다.

## 3. RewardType

| 값 | 저장 문자열 | 선택 가능 | 용도 |
|---|---|---:|---|
| `title` | `title` | 예 | 내 정보에 적용할 칭호 |
| `accessory` | `accessory` | 예 | 한걸음이 장식 |
| `theme` | `theme` | 예 | 홈 배경 테마 |
| `expression` | `expression` | 아니요 | 획득 뒤 축하 표현 |
| `unknown` | `unknown` | 아니요 | 미래 타입의 안전한 파싱 |

특별 표정은 현재 선택 슬롯을 만들지 않는다. 장식은 향후 머리·얼굴·목·옆면 슬롯 확장을 위해 선택 ID 집합으로 저장한다.

## 4. RewardDefinition과 카탈로그

`RewardDefinition`은 `rewardId`, `rewardType`, `title`, `description`, `requiredPoints`, `assetKey`, `sortOrder`, `isActive`, `rewardVersion`을 가진다. 빈 ID, 음수 점수·정렬값, 1보다 작은 보상 버전을 거부한다.

| 점수 | 안정 ID | 종류 | 표시 이름 |
|---:|---|---|---|
| 100 | `title_first_step` | 칭호 | 첫걸음 시작 |
| 300 | `accessory_scarf` | 장식 | 한걸음이 목도리 |
| 500 | `theme_sage` | 테마 | 편안한 세이지 |
| 800 | `title_steady_learner` | 칭호 | 꾸준한 연습생 |
| 1,200 | `accessory_hat` | 장식 | 한걸음이 모자 |
| 1,600 | `theme_sky` | 테마 | 맑은 하늘 |
| 1,600 | `accessory_glasses` | 장식 | 한걸음이 안경 |
| 2,000 | `title_digital_confidence` | 칭호 | 디지털 자신감 |
| 3,000 | `theme_peach` | 테마 | 따뜻한 복숭아 |
| 3,000 | `accessory_bag` | 장식 | 한걸음이 가방 |
| 5,000 | `title_hangeoreum_master` | 칭호 | 한걸음 달인 |
| 5,000 | `expression_celebration` | 표정 | 특별 축하 표정 |

카탈로그는 점수와 고유 `sortOrder`로 안정 정렬한다. ID·정렬값 중복과 지원하지 않는 타입을 거부한다. ID, 종류, 현재 포인트 이하 보상, 다음 기준과 같은 기준의 복수 보상을 조회할 수 있다. 기본 조회는 비활성 보상을 제외하지만 이미 저장된 비활성 획득 ID는 상태 정규화에서 삭제하지 않는다. 외부에는 수정 불가능한 목록을 제공한다.

## 5. RewardState

상태에는 획득 ID 집합, ID별 획득 UTC 시각, 축하 완료 ID, 선택한 칭호, 선택한 장식 ID 집합, 선택한 테마, 소급 지급 완료 여부, 데이터·카탈로그 버전이 들어간다.

- 집합으로 중복 ID를 제거한다.
- 알 수 없는 미래 획득 ID는 보존한다.
- 잘못된 획득 시각만 제외하고 획득 자체는 유지한다.
- 축하 완료 ID는 획득 ID와의 교집합으로 정규화한다.
- 선택값은 획득했고 현재 카탈로그의 타입과 일치할 때만 유지한다.
- `null` 칭호·테마와 빈 장식 집합은 무료 기본 상태다.
- 음수 버전은 0으로 읽는다.

## 6. 실제 저장 키

| 키 | 형식 |
|---|---|
| `v3_reward_data_version` | int |
| `v3_reward_catalog_version` | int |
| `v3_reward_unlocked_ids` | StringList |
| `v3_reward_unlocked_at_json` | JSON String |
| `v3_reward_celebrated_ids` | StringList |
| `v3_reward_selected_title_id` | String |
| `v3_reward_selected_accessory_ids` | StringList |
| `v3_reward_selected_theme_id` | String |
| `v3_reward_retroactive_grant_version` | int |
| `v3_reward_migration_version` | int |
| `v3_reward_state_pending_json` | JSON String |

문자열은 `V3RewardKeys`에 한 번만 선언한다. 기존 `digital_confidence_points`와 migration metadata 키는 바꾸지 않는다.

## 7. RewardRepository

저장소는 빈 상태 읽기, 전체 저장·복원, 칭호·장식·테마 선택, 축하 완료, 전체 포인트 보상 상태 초기화를 제공한다.

1. 정규화한 전체 후보를 pending JSON에 기록한다.
2. pending을 다시 읽어 같은 값인지 검증한다.
3. 획득·시각·축하·선택과 버전을 개별 키에 기록한다.
4. 저장값을 다시 `RewardState`로 읽어 후보와 비교한다.
5. 검증 뒤 pending을 제거한다.

중간 쓰기가 실패하면 예외를 반환하고 pending을 남긴다. 다음 `load()`가 같은 후보를 멱등 복구한다. 미래 데이터 버전은 저장으로 덮어쓰지 않고 미래 pending도 제거하지 않는다. 민감 데이터나 전체 Preferences 값은 로그로 출력하지 않는다.

저장소가 명시적으로 호출되기 전에는 어떤 보상 키도 생기지 않는다. 획득하지 않은 보상, 존재하지 않는 ID, 타입이 다른 보상은 선택할 수 없다.

## 8. 손상 복구

- 잘못된 JSON·목록 형식은 해당 필드의 빈 기본값으로 읽는다.
- 중복 획득 ID는 하나로 정리한다.
- 잘못된 날짜 문자열은 시각만 제외한다.
- 획득하지 않은 축하 완료·선택 상태는 제거한다.
- 장식을 테마나 칭호로 선택한 값은 기본값으로 복구한다.
- 알 수 없는 미래 획득 ID는 보존하고 화면 후보에서만 제외한다.
- 음수 버전은 0으로 읽는다.
- 미래 버전은 비파괴적으로 읽고 현재 저장소로 덮어쓰지 않는다.
- 손상된 pending만 제거하며 전체 SharedPreferences나 V2 기록을 지우지 않는다.

## 9. 기록 초기화

`연습 기록 초기화`는 이미 존재하는 `v3_reward_*` 상태 키를 제거한다. 획득·시각·축하·선택·소급 상태와 보상 데이터·카탈로그 버전이 함께 초기화된다. 보상 키가 없으면 새 키를 만들지 않는다.

전체 schema version과 완료 migration revision, 글자 크기, 선명한 화면, 온보딩 완료 상태, 향후 TTS와 일반 앱 설정은 유지한다.

## 10. 데이터 버전과 다음 단계

모델과 저장소 코드는 기존 사용자 데이터를 변경하지 않으므로 전체 schema version은 계속 `1`, 완료 revision은 `v3_foundation_1`이다. 앱 실행만으로 160점 사용자가 `title_first_step`을 받지 않으며 `v3_reward_*` 키도 생성되지 않는다.

다음 단계는 schema version `2`, revision ID `v3_reward_backfill_2`를 후보로 한다. 현재 `DataMigrationCoordinator` 실행 목록에는 등록하지 않았으며 실제 이름과 트랜잭션 경계는 구현 시 다시 검증한다.

## 11. 테스트 범위

- 12개 ID·점수·정렬·같은 기준 복수 보상
- ID·종류·현재 점수·다음 기준 조회와 비활성 처리
- 정의·상태 JSON 왕복, 동등성, 미래 ID 보존
- 빈 저장소 무쓰기
- 저장·재실행 복원과 선택 타입 검증
- 축하 완료 중복 방지
- 손상 JSON·날짜·선택 복구
- pending 중단 복구와 저장 실패 주입
- 미래 데이터 버전 비파괴 처리
- 보상 초기화와 V2·migration metadata 보존
- 160점 fixture에서 자동 지급·키 생성 없음

Provider·화면·완료 보상 연결 테스트는 실제 소급 지급과 UI 구현 단계에서 추가한다.
