# 한걸음 디지털 V3 데이터 마이그레이션 설계

## 1. 목표

V2 사용자가 V3로 업데이트해도 포인트, 완료 횟수, 배지, 최근 기록, 오늘의 미션, 접근성 설정과 온보딩 상태가 그대로 유지되어야 한다. 마이그레이션은 반복 실행해도 결과가 같은 멱등 작업이어야 하며 실패를 데이터 삭제로 처리하지 않는다.

## 2. 변경하지 않는 V2 데이터

V3는 현재 코드에 선언된 다음 범주의 SharedPreferences 키를 이름과 의미 그대로 유지한다.

- 전체 포인트
- 7개 콘텐츠와 병원 세부 업무의 따라 하기·혼자 하기 완료 횟수
- 첫 완료 배지
- 최근 연습 기록
- 완료 세션 보상 중복 방지 값
- 자유·따라·혼자 연습 모드 상태
- 오늘의 미션 날짜
- 선택된 미션 ID
- 완료된 미션 ID
- 추가 보상이 지급된 미션 ID
- 완료 시각
- 전날 미션 조합
- 콘텐츠 선정 빈도
- 활성 미션 ID
- 글자 크기
- 화면 대비
- 온보딩 완료 상태

정확한 문자열은 `lib/core/data_migration/preference_keys.dart`의 `V2PreferenceKeys`를 단일 진실 공급원으로 사용한다. 기존 Provider도 이 상수를 참조하므로 저장된 키 이름은 바뀌지 않는다. 전체 실제 키와 분류는 [V3 데이터 버전 구현](V3_데이터_버전_구현.md)에 정리한다.

## 3. V3 신규 키 규칙

새 키는 `v3_` 접두사와 명시적 버전을 사용한다.

| 실제 키 | 용도 | 민감도 |
|---|---|---|
| `v3_data_schema_version` | 완료된 로컬 스키마 버전 | 낮음 |
| `v3_migration_pending_revision` | 실행 중이거나 재실행할 revision 번호 | 낮음 |
| `v3_migration_completed_revisions` | 검증까지 완료된 안정 revision ID 목록 | 낮음 |
| `v3_migration_last_success_revision` | 마지막 성공 revision 번호 | 낮음 |
| `v3_migration_last_outcome` | `migrated`, `alreadyCurrent`, `recovered`, `failed` 중 마지막 결과 | 낮음 |
| `v3_audio_enabled` | 음성 안내 사용 여부 | 낮음 |
| `v3_audio_rate` | 느리게/보통 | 낮음 |
| `v3_notice_last_read_version` | 마지막으로 읽은 번들 공지 | 낮음 |
| `v3_installation_id` | 향후 멱등 업로드용 무작위 ID | 선택, 서버 도입 전 생성하지 않음 |
| `v3_entitlement_cache` | 향후 권한 캐시 | 실제 결제 도입 전 저장하지 않음 |

인증 토큰, 구매 토큰, 이메일은 SharedPreferences에 저장하지 않는다.

## 4. 최초 V3 실행 절차

1. `SharedPreferences`를 준비하고 저장된 schema와 완료 revision을 읽는다.
2. 앱보다 높은 미래 schema를 발견하면 어떤 값도 수정하지 않고 종료한다.
3. 다음 revision 번호를 `v3_migration_pending_revision`에 먼저 기록한다.
4. 기존 값의 타입과 범위를 검사하고 안전하게 복구 가능한 손상 값만 정규화한다.
5. revision의 저장 결과를 다시 검증한다.
6. revision ID를 `v3_migration_completed_revisions`에 기록한다.
7. `v3_data_schema_version`과 마지막 성공 revision을 갱신한다.
8. pending revision을 마지막에 제거한다.

마이그레이션 중 앱이 종료되면 pending revision이 남는다. 다음 실행은 같은 멱등 revision을 다시 적용하고 검증한다. 정상 V2 값은 다시 쓰지 않으며, 포인트 보상 관련 `v3_reward_*` 키도 이번 revision에서 만들지 않는다.

## 5. 타입과 손상 데이터 처리

- 정상 타입의 기존 값은 그대로 보존한다.
- 음수 포인트·완료 횟수와 잘못된 숫자 타입은 기존 Provider의 안전 기본값과 같은 `0`으로 정규화한다.
- 최근 기록 목록은 정상 JSON 항목의 순서를 유지하고 손상된 항목만 제외한다.
- 오늘의 미션 날짜·3개 ID 조합이 손상되면 현재 날짜 상태만 제거해 기존 Provider가 정상 조합을 다시 만들게 한다. 빈도·완료 시각 JSON은 유효한 기존 항목만 보존한다.
- 잘못된 접근성·온보딩 타입은 해당 키만 제거해 기존 기본값으로 복구하며 다른 설정은 유지한다.
- completed/pending/schema metadata가 손상되면 metadata만 복구하고 revision을 다시 검증한다.
- 앱보다 높은 미래 schema는 삭제하거나 낮추지 않는다.
- 실패 결과에는 오류 종류만 구조화해 반환하며 Preferences 전체 값이나 민감값을 로그로 남기지 않는다.

## 6. V3 신규 콘텐츠 데이터

- 신규 콘텐츠는 기존 ID와 충돌하지 않는 영문 소문자 ID를 사용한다.
- 완료 횟수, 배지, 보상 토큰은 콘텐츠 ID와 모드가 포함된 V3 전용 키를 사용한다.
- 오늘의 미션 카탈로그에 추가할 때 기존 미션 ID를 바꾸지 않는다.
- 카탈로그 버전을 저장해 미션 후보 변경과 사용자의 오늘 미션 고정을 분리한다.
- 같은 날짜에 앱이 업데이트되어도 이미 선정된 3개는 유지한다.

## 7. 향후 로그인 도입 시 병합

### 7.1 최초 연결

로그인 직후 자동 덮어쓰지 않고 다음을 보여준다.

- 이 기기의 포인트와 완료 기록
- 계정에 이미 저장된 기록 유무
- 병합 결과의 개요
- 연결 취소 선택

### 7.2 권장 병합 규칙

| 데이터 | 병합 규칙 |
|---|---|
| 완료 이벤트 | 고유 이벤트 ID 합집합 |
| 포인트 | 이벤트를 재계산하고 같은 이벤트 중복 제외 |
| 완료 횟수 | 고유 완료 이벤트 개수 |
| 배지 | 획득 조건을 만족한 배지 합집합 |
| 최근 기록 | ID 중복 제거 후 시간순, 최대 개수 제한 |
| 오늘의 미션 | 한국 날짜와 미션 ID별 완료 합집합 |
| 글자 크기·대비 | 기기별 유지, 계정 동기화 기본 제외 |

기존 V2 기록에는 이벤트 ID가 없으므로 최초 업로드 시 `installation_id + key + ordinal`을 이용한 결정적 import ID를 생성한다. 같은 기기에서 재시도해도 동일 ID가 만들어져야 한다. 서버는 import batch ID와 이벤트 ID에 고유 제약을 둔다.

### 7.3 여러 기기 충돌

- 증가형 카운터 자체를 합산하지 않는다.
- 서버가 수신한 이벤트 집합에서 카운터를 계산한다.
- 배지는 취소하지 않고 합집합을 사용한다.
- 최근 기록 정렬에는 서버 수신 시각이 아니라 이벤트 발생 시각과 오프라인 여부를 함께 둔다.
- 기기 시간이 크게 어긋나면 순서를 보정하되 기록을 삭제하지 않는다.

## 8. 로그아웃과 회원 탈퇴

### 로그아웃

- 서버 세션과 보안 저장소의 토큰을 삭제한다.
- 로컬 연습 기록을 유지할지 이 기기에서 지울지 명시적으로 선택하게 한다.
- 선택 전에는 로컬 데이터를 자동 삭제하지 않는다.
- 로그아웃 뒤에도 기존 무료 연습은 사용할 수 있다.

### 회원 탈퇴

- 서버 계정 접근을 즉시 차단한다.
- 법적 보존 의무가 없는 연습 데이터와 문의 데이터를 정해진 기간 안에 삭제한다.
- 결제 사업자가 보유하는 거래 기록은 별도 정책과 보존 의무를 안내한다.
- 기기 데이터도 지울지 별도로 확인한다.
- 탈퇴 완료와 복구 가능 기간을 명확히 표시한다.

## 9. 삭제와 보유 정책 초안

| 데이터 | 기본 위치 | 보유 | 삭제 |
|---|---|---|---|
| V2 연습 기록 | 기기 | 사용자가 초기화/앱 삭제 전 | 기존 기록 초기화 |
| 접근성·온보딩 | 기기 | 앱 삭제 전 | 기록 초기화에서는 유지 |
| TTS 설정 | 기기 | 기능 사용 기간 | 연습 기록 초기화에서는 유지 |
| 공지 읽음 상태 | 기기 | 공지 버전 유효 기간 | 캐시 정리 가능 |
| 향후 계정 기록 | 서버 | 계정 유지 기간 | 탈퇴 정책에 따라 삭제 |
| 문의 | 이메일/서버 | 답변·분쟁에 필요한 최소 기간 | 기간 만료 또는 요청 시 삭제 |
| 인증 토큰 | 보안 저장소 | 세션 기간 | 로그아웃·탈퇴 즉시 삭제 |

## 10. 실패 복구와 롤백

- 배포 전 V2 상태 fixture를 보관하고 V3 업그레이드 테스트에 사용한다.
- 마이그레이션 완료 마커는 모든 검증 뒤 마지막에 쓴다.
- 신규 기능 플래그를 끄면 V2 UI와 데이터 읽기가 그대로 동작한다.
- V3 앱을 제거하고 V2를 다시 설치하면 Android 앱 데이터 호환이 항상 보장되는 것은 아니므로 앱 다운그레이드를 복구 전략으로 삼지 않는다.
- 실패 시 사용자에게 기록 초기화를 권하지 말고 재시도와 지원 경로를 제공한다.
- 원격 동기화 도입 뒤에는 서버 import batch를 취소할 수 있는 관리자 작업과 감사 로그가 필요하다.

## 11. 자동 테스트 계획

### 기준 fixture

- 신규 설치
- V2 포인트·횟수·배지·최근 기록이 모두 있는 상태
- 오늘 미션 일부 완료와 보상 지급 상태
- 아주 큰 글씨·선명한 화면·온보딩 완료 상태
- 일부 알 수 없는 미래 ID가 섞인 상태
- 마이그레이션 중간 종료 상태

### 필수 검증

1. 최초 실행 후 V2 모든 값이 동일하다.
2. 마이그레이션을 여러 번 실행해도 신규 키와 포인트가 중복되지 않는다.
3. pending revision 상태에서 재시작하면 안전하게 완료한다.
4. 쓰기 실패 시 기존 키가 그대로 남는다.
5. 기록 초기화는 연습 데이터와 오늘 미션을 초기화하지만 접근성·온보딩·V3 음성 설정은 유지한다.
6. 로그인 없는 상태에서 모든 V2 콘텐츠가 오프라인으로 동작한다.
7. 향후 최초 업로드를 재시도해도 같은 import ID로 중복 생성되지 않는다.
8. 로그아웃 선택에 따라 로컬 유지/삭제가 정확히 구분된다.
9. 앱 업데이트 후 기존 183개 테스트와 신규 마이그레이션 테스트가 모두 통과한다.

## 12. 구현 완료 조건

- V2 SharedPreferences 상수 변경 없음
- V2 기록 스냅샷의 업데이트 전후 동등성 확인
- 마이그레이션 멱등성과 중단 복구 테스트 통과
- 로그인 없이 오프라인 사용 가능
- 실패 시 기록 초기화나 데이터 손실 없음
- 개인정보와 인증 토큰을 Preferences 및 로그에 저장하지 않음
- 실제 기기에서 기존 앱 데이터가 있는 상태로 업데이트 설치 검증
- revision 1은 데이터 버전 기반만 구성하며 포인트 보상 카탈로그와 소급 지급을 수행하지 않음

## 13. 포인트 혜택 마이그레이션

기존 포인트 키 `digital_confidence_points`는 변경하지 않는다. V3 최초 실행 시 현재 점수를 기준으로 받을 수 있는 모든 보상 ID를 계산하고, 획득 목록과 획득 시각을 신규 `v3_reward_*` 키에 기록한다. 초기 기준과 안정 ID는 `100:title_first_step`, `300:accessory_scarf`, `500:theme_sage`, `800:title_steady_learner`, `1200:accessory_hat`, `1600:theme_sky + accessory_glasses`, `2000:title_digital_confidence`, `3000:theme_peach + accessory_bag`, `5000:title_hangeoreum_master + expression_celebration`이며 보상 카탈로그를 단일 진실 공급원으로 사용한다.

점수 계산은 V2와 동일하게 자유 연습 0점, 따라 해보기 10점, 혼자 해보기 20점을 유지한다. 오늘의 미션은 혼자 해보기 기본 20점과 추가 10점이고, 추가 보상은 하루 최대 30점이므로 세 미션을 모두 완료했을 때 기본 보상을 포함한 하루 최대 점수는 90점이다. 마이그레이션은 점수를 새로 계산하거나 차감하지 않는다.

### 소급 지급 규칙

1. 현재 총점을 읽는다.
2. 카탈로그 버전과 이미 획득한 ID를 읽는다.
3. 기준 이하이면서 미획득인 보상만 계산한다.
4. 여러 보상은 하나의 소급 축하 묶음으로 기록한다.
5. 포인트, 기존 배지와 최근 기록은 변경하지 않는다.
6. 카탈로그 버전의 소급 안내 완료 값을 마지막에 기록한다.

160점 사용자는 100점 `첫걸음 시작`을 획득하지만 포인트는 160점으로 유지된다. 기존 배지·최근 기록·완료 횟수도 유지한다. 이미 일부 보상을 가진 경우에는 기존 ID와 새 계산 결과의 합집합만 저장한다. 중간 종료 뒤 재실행해도 보상 ID나 소급 안내가 중복되지 않아야 한다. 손상된 획득 목록은 총점과 정적 카탈로그를 이용해 복구하되 선택값은 실제 획득한 ID일 때만 유지한다.

### 초기화

현재 `연습 기록 초기화`에 다음 V3 키를 추가한다.

- 획득한 포인트 보상 ID와 시각
- 축하 완료·대기 상태
- 적용한 칭호
- 적용한 캐릭터 장식
- 적용한 홈 테마
- 보상 마이그레이션 완료 상태

초기화 뒤 총점 0을 기준으로 다시 평가한다. 글자 크기, 화면 대비, 온보딩 상태, 음성 안내와 일반 앱 설정은 계속 유지한다. 구독 혜택과 포인트 보상은 별도 데이터로 관리한다. 다음 앱 실행에서 초기화 전 보상을 소급 복구하지 않도록 보상 상태와 총점 초기화를 같은 작업 흐름에서 처리한다.

보상 저장 키는 `v3_reward_data_version`, `v3_reward_catalog_version`, `v3_reward_unlocked_ids`, `v3_reward_unlocked_at_json`, `v3_reward_celebrated_ids`, `v3_reward_selected_title_id`, `v3_reward_selected_accessory_ids`, `v3_reward_selected_theme_id`, `v3_reward_retroactive_grant_version`, `v3_reward_migration_version`으로 통일한다. `v3_reward_state_pending_json`에 후보 상태와 revision을 먼저 기록해 검증한 뒤 개별 키를 갱신하고 데이터·마이그레이션 버전을 마지막에 쓴다. 앱이 중간에 종료되면 pending revision과 완료 버전을 비교해 같은 작업을 멱등 재실행하므로 부분 저장을 완료로 오인하지 않는다.

`RewardDefinition`은 `rewardId`, `rewardType`, `title`, `description`, `requiredPoints`, `assetKey`, `sortOrder`, `isActive`, `rewardVersion`을 사용한다. `RewardState`는 획득 ID·시각, 축하 완료 ID, 선택한 칭호·장식·테마, 소급 지급 상태와 데이터 버전을 사용한다. 표시 이름이나 기준이 바뀌어도 안정 ID는 변경하지 않으며 이미 획득한 보상은 회수하지 않는다.

현재는 모델·카탈로그·저장소와 기록 초기화 키 연결만 구현했다. 저장소를 호출하지 않는 앱 시작은 어떤 `v3_reward_*` 키도 만들지 않으며 160점 등 기존 포인트를 읽어 보상을 지급하지 않는다. 실제 소급 지급은 제안 revision `v3_reward_backfill_2`에서 추가하고, 그전까지 schema version `1`과 완료 revision `v3_foundation_1`만 유지한다. 구현 상세는 [V3 포인트 데이터 모델 구현](V3_포인트_데이터_모델_구현.md)을 따른다.
