# V3 데이터 버전 구현

## 1. 구현 범위

V3 첫 단계는 기존 V2 데이터를 안전하게 읽고 검증하는 데이터 버전 기반을 구현했다. 현재 schema version은 `1`, 완료 revision ID는 `v3_foundation_1`이다. 다음 단계에서 포인트 혜택 모델·정적 카탈로그·저장소를 코드로 추가했지만 앱 시작 migration에는 등록하지 않았다. 기존 포인트 소급 지급, 자동 보상 해제, 칭호·장식·테마 UI 적용, TTS, 신규 콘텐츠, 로그인과 서버 기능은 포함하지 않는다.

구현 위치는 `lib/core/data_migration/`이며 앱 시작 시 `SharedPreferences`를 준비한 뒤 Provider를 만들기 전에 실행한다.

## 2. 실제 migration metadata

| 키 | 타입 | 용도 |
|---|---|---|
| `v3_data_schema_version` | int | 검증까지 완료된 schema version |
| `v3_migration_pending_revision` | int | 실행 중이거나 재실행할 revision 번호 |
| `v3_migration_completed_revisions` | StringList | 완료된 안정 revision ID |
| `v3_migration_last_success_revision` | int | 마지막 성공 revision 번호 |
| `v3_migration_last_outcome` | String | 마지막 구조화 결과 이름 |

지원 버전보다 높은 schema 또는 pending revision은 수정하거나 다운그레이드하지 않는다. metadata는 연습 기록 초기화 대상이 아니다.

## 4. 실행 순서와 중단 복구

1. 저장된 schema, pending revision, 완료 revision ID를 읽는다.
2. 완료하지 않은 다음 revision을 선택한다.
3. pending revision을 기록한다.
4. revision을 적용한다.
5. 저장된 값을 다시 검증한다.
6. 완료 revision ID를 기록한다.
7. schema와 마지막 성공 revision을 기록한다.
8. pending revision을 제거한다.

SharedPreferences는 트랜잭션을 제공하지 않으므로 각 작업은 멱등이어야 한다. pending 기록 직후, 데이터 저장 뒤, 완료 ID 기록 전, schema 기록 전, pending 제거 전에 종료돼도 다음 실행에서 같은 revision을 안전하게 다시 수행한다. 이미 완료 목록에 든 revision은 다시 적용하지 않는다.

## 5. revision 1의 손상 복구

- 정상 V2 값은 쓰거나 변환하지 않는다.
- 음수 또는 잘못된 타입의 포인트·완료 횟수는 `0`으로 복구한다.
- 잘못된 bool과 enum 설정은 해당 키만 제거해 기존 Provider 기본값을 사용한다.
- 최근 기록은 정상 JSON 항목의 순서를 보존하고 손상 항목만 제외한다.
- 현재 미션 날짜나 3개 ID 조합이 잘못되면 현재 미션 상태만 제거한다.
- 완료·보상·활성 미션은 현재 3개 조합과 일치하는 값만 유지한다.
- 미션 완료 시각과 선정 빈도 JSON은 유효한 항목만 유지한다.
- 손상된 migration metadata는 metadata만 복구한다.
- 미래 schema는 어떤 사용자 데이터도 수정하지 않는다.
- Preferences 전체 내용, PIN, 개인정보는 로그에 출력하지 않는다.

실패 결과는 `DataMigrationResult`에 상태, 오류 종류와 메시지로 반환한다. pending revision은 다음 실행의 복구 표식으로 남고 앱은 기존 V2 읽기 경로로 계속 시작한다.

## 6. 신규 설치와 기록 초기화

빈 저장소에서는 migration metadata만 기록한다. V2 포인트·설정·기록 키와 `v3_reward_*` 키를 미리 만들지 않는다. 이후 기존 Provider가 온보딩과 오늘의 미션을 원래 흐름대로 초기화한다.

연습 기록 초기화는 기존 포인트, 완료 횟수, 배지, 최근 기록과 오늘의 미션 상태를 지운다. schema와 완료 revision 목록은 유지하므로 revision 1을 다시 실행하지 않는다. 글자 크기, 화면 대비와 온보딩 완료 상태도 기존 정책대로 유지한다.

## 7. 자동 테스트 fixture

`test/data_migration_test.dart`는 다음을 검증한다.

- 빈 저장소 첫 실행과 두 번째 실행
- 160점, 모든 완료 횟수, 배지, 최근 기록 순서, 미션, 접근성, 온보딩 상태 보존
- 다섯 중단 지점별 pending revision 복구
- 음수·잘못된 숫자, 손상된 최근 기록과 미션 JSON 복구
- 손상된 schema·pending·완료 revision metadata와 완료 목록의 중복·알 수 없는 ID 복구
- 미래 schema 비파괴 처리
- 기록 초기화 뒤 schema·완료 revision·설정 유지와 미션 재생성
- 포인트 보상 `v3_reward_*` 키가 생성되지 않음

현재 전체 검증은 V2 기준선 183개와 신규 12개를 합한 195개 테스트다.

## 8. 다음 revision 추가 방법

1. `DataMigrationRevision`을 구현하고 증가한 version과 영구적인 고유 ID를 부여한다.
2. 적용 로직을 반복 실행해도 결과가 같게 만든다.
3. 저장 뒤 상태를 확인하는 `verify`를 구현한다.
4. `DataMigrationCoordinator`의 revision 목록과 current schema를 함께 올린다.
5. 각 중단 지점, 기존 값 보존, 손상 복구 fixture를 추가한다.
6. 기록 초기화 대상인지 metadata인지 명시한다.

예정된 schema version `2`, revision ID `v3_reward_backfill_2`는 기존 포인트 소급 지급만 별도 구현한다. 현재 실행 목록에는 등록하지 않았으며 revision 1은 보상 ID를 계산하거나 보상을 지급하지 않는다. 모델·카탈로그·저장소의 구현 범위는 [V3 포인트 데이터 모델 구현](V3_포인트_데이터_모델_구현.md)을 따른다.
